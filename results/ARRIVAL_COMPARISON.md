# 9000条消息：不重不漏、标记正确、秒级可见

**目标是让每次原始输入只输出一次、不漏消息、重复标记正确，同时让下游在秒级看到消息。**“不重”指故障恢复不能额外多写；原本就输入了三次的同一个业务 ID，三次都要保留。

这次用同一套规则测试三种主要方案：Flink 事务写 Kafka、Redis 配合普通 Kafka 写入、直接 Kafka Streams EOS。每种方案都测了正常运行和故障恢复，完整重复了两轮。

**本次两轮实验中，直接 Streams EOS 保持了9000条输出且标记正确；正常运行99%的消息在约6.5～6.9秒内可见，包含崩溃恢复时为约18.6～20.3秒。**这说明当前原型达到数秒量级的正常可见延迟，还没有证明1秒以内可见。Flink 事务方案同样保持消息正确，但本次 CK＝30秒，正常可见等待约为几十秒。Redis 先登记方案则在恢复后多写了消息。下面分别列出条数和实际等待时间。

## 先说清楚这9000条

**一共9000条输入，包含3000个业务 ID，每个 ID 出现三次。重复消息也必须输出。**

比如同一个 ID 来三次，下游应收到三条：第一条标“首次”，后两条标“重复”。JSON 中分别写成 `is_duplicate=false` 和 `is_duplicate=true`。

**正确结果：下游一共收到9000条，其中3000条标“首次”、6000条标“重复”；即使程序出故障再恢复，也应该保持这个结果。**

## 最后收到多少条，重复标记是否正确

下面的条数在两轮实验中完全一致，消息内容、每次输入的输出次数和重复标记均逐条核对。这里统计的是下游业务消费者真正能读到的消息。

| 方案 | 正常时收到 | 故障恢复后收到 | 恢复后的首次 / 重复标记 | 不重不漏且标记正确？ |
|---|---:|---:|---:|---|
| Flink 事务写 Kafka（CK＝30秒） | 9000条 | 9000条 | 3000 / 6000条 | 是，两轮均正确 |
| 直接 Kafka Streams EOS | 9000条 | 9000条 | 3000 / 6000条 | 是，两轮均正确 |
| Redis 先登记，再普通写 Kafka | 9000条 | 14402条 | 3000 / 11402条 | 否，额外收到5402条 |
| Redis 先写 Kafka，收到成功回复后再登记 | 尚未测试 | 尚未测试 | 尚未测试 | 本次缺少这项结果 |

正常运行时，三个已测方案都是9000条，标记都是3000条首次、6000条重复。

**Redis 先登记方案的问题在恢复后：原来的9000条都还在，另外多出了5402条重放消息。**这5402条也被标成了重复，所以最终变成3000条首次、11402条重复，总共14402条。它没有达到“原始每次输入只输出一次”的目标。

## 正常运行时，下游等多久能看到

从“发送这条输入消息”开始计时，到“下游消费者第一次读到这条输出消息”为止。因此这里包含处理、排队、写入 Kafka 和事务提交等待，表示实际端到端可见时间。

| 方案 | 一半消息在多久内可见（p50） | 99%的消息在多久内可见（p99） |
|---|---:|---:|
| Flink 事务写 Kafka（CK＝30秒） | 26.7～27.8秒 | 28.2～29.1秒 |
| 直接 Kafka Streams EOS | 5.7～6.0秒 | 6.5～6.9秒 |
| Redis 先登记，再普通写 Kafka | 38.0～41.0秒 | 68.5～71.8秒 |
| Redis 写成功后再登记 | 尚未测试 | 尚未测试 |

表中范围是两轮测得的分位数，例如“5.7～6.0秒”表示两轮 p50 分别落在这个范围，不是每条消息都恰好等这么久。Redis 当前逐条同步执行，未做批量优化，这个速度不代表 Redis 的性能上限。

## 如果发生故障，多久能看到

这一张表把故障、停机恢复和重放等待也算进去。故障恢复的时间与正常延迟分开看。

| 方案 | 一半输出在多久内可见（p50） | 99%的输出在多久内可见（p99） |
|---|---:|---:|
| Flink 事务写 Kafka（CK＝30秒） | 33.8～48.5秒 | 35.1～49.8秒 |
| 直接 Kafka Streams EOS | 18.3～19.9秒 | 18.6～20.3秒 |
| Redis 先登记，再普通写 Kafka | 53.4～58.0秒 | 99.3～103.9秒 |
| Redis 写成功后再登记 | 尚未测试 | 尚未测试 |

Redis 故障行统计实际收到的14402条输出，包含额外重放；其他两行各统计9000条。Flink 的故障是一次真实 CK 异常导致自动恢复；直接 Streams 的故障是消息写入获确认、但事务尚未提交时杀死并重启本实验进程。两者不是完全相同的故障注入方式。

## CK＝30秒和 Streams＝100ms，分别是什么意思

- **Flink 事务写入：等对应 CK 成功，提交后下游才能看到那一批消息。** 本次 CK 是30秒。如果配置成3分钟，提交等待就受3分钟的 CK 周期及 CK 完成耗时影响；单条消息等待多久还取决于它在周期中的位置。
- **Streams EOS：以100ms为目标周期提交 Kafka 事务，不需要等 Flink CK。** 这是提交周期；本次实测端到端 p50 仍为5.7～6.0秒，尚未达到100ms端到端可见。
- 如果 Streams 前面仍接着一个要等 CK 的 Flink 事务输出，它仍要先等上游把消息提交出来。

## 之前表里的18000条，是哪来的

18000条来自一项额外的串联对照：**Flink 普通转发→中间 Kafka→Streams EOS**。这项对照与直接 Streams 的9000条结果分开看。

1. 先完成一次没有业务消息的 CK，保存进度0。
2. 输入9000条，Flink 普通转发先写出9000条。
3. 下一次 CK 失败，作业恢复到进度0，又把这9000条写了一遍。
4. 中间 Kafka 已经有18000条，后面的 Streams 因而收到18000条、输出18000条。

**直接 Streams EOS 两轮始终是9000条输入、9000条已提交输出，标记正确。**串联对照的18000条说明上游重放已经多写，整条链路没有达到目标。

## Redis 两种顺序，目前测到了哪一步

- **先登记：** 查 Redis→登记“见过”→发送 Kafka。本次已测，两轮 CK 失败恢复后均为14402条。
- **后登记：** 查 Redis→发送 Kafka→收到成功回复→登记“见过”。当前保留全部消息的实验尚未测试。

两步之间发生故障时，先登记可能使首次消息在恢复后被错标为重复；后登记可能让已经写出的首次消息再被写出、并再次标为首次。这些是两种顺序需要单独验证的窗口，本次 CK 失败没有逐一覆盖它们。此前 [过滤重复 ID 的实验](DEDUPLICATION.md) 测过两种顺序，但那里的重复消息会跳过输出，结果不能套用到这次。

## 实验范围和完整记录

本次为合成 JSON，单机、单分区、处理并行度1，四线程目标每秒发送3000条，约3秒发完9000条。配置了1小时重复判断窗口，但没有实际等待1小时测试到期。这是短批次实验，没有证明长期稳定吞吐或生产延迟；首次业务处理路径也未单独做充分预热。

“下游可见”按 `read_committed` 消费者统计。原始 Kafka 日志可能保留中止事务的数据，不能把它的条数当成业务消费者最终收到的条数。
